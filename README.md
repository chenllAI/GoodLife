# 家务积分榜 🏆

给小良和小影的家庭家务积分工具。做家务 → 记一笔 → 攒积分 → 上榜单。

- **打开链接就能看** —— 不需要任何注册或配置
- **移动端优先**，手机上就是原生应用的手感
- **日榜 / 周榜 / 月榜**，外加积分走势、分类对比
- **30 项预置家务**，按难易程度分好分值；也能自己加
- **新增家务自动配图标**（输入"洗窗帘"，自动认出来是 🪟）
- **全家读写同一份数据**，存在这个 GitHub 仓库里
- **没有服务器，没有数据库**，账号密码都不用注册

---

## 一、怎么用

### 看榜单：什么都不用做

把网页链接发给任何人，打开就能看。不需要注册、不需要填任何东西。

### 记分：每台设备填一次令牌

打开链接 →「设置」→ 填一个访问令牌 → 保存。之后这台设备就能记分了。

**但不用每台设备都这么做。** 一台设备填好之后，在设置里点「🔗 邀请链接」，
把生成的链接发到家人手机上，对方**打开一次就自动配置好**，什么都不用填。

> 邀请链接把令牌放在 URL 的 `#` 之后（fragment）。fragment 不会发给服务器，
> 所以它不会出现在 GitHub Pages 的访问日志里。应用读到后会立刻把它从地址栏清掉。
>
> 这条链接等同于仓库的写权限，**只发给家里人**。万一发错了，去 GitHub 撤销
> 那个令牌就行，数据本身不会有事。

## 二、数据存在哪

```
chenllAI/GoodLife          ← 代码和数据在同一个仓库
├── src/                   代码
├── .github/workflows/     部署流程
└── data/                  ← 数据（应用自动读写，你不用管）
    ├── meta.json              成员、家务目录、设置
    └── records/
        ├── records-2026-09.json   这个月的积分明细
        └── records-2026-08.json   上个月的
```

**按月分文件**有三个原因：GitHub 单文件有 1MB 上限（不分片约一年就会撞上）；
家务改动落在 `meta.json`、记账落在月度分片，不同文件天然减少冲突；读取时可以
只取需要的月份，省限流额度。

### ⚠️ 为什么部署流程里有 `paths-ignore: data/**`

**每记一笔家务就是一次提交。** 如果部署流程不加这个过滤，每记一笔家务都会触发
一次完整的构建 + 部署 —— GitHub Pages 免费版每小时只允许约 10 次，一个忙碌的
晚上就能把额度打爆，之后连正常的代码更新都部署不上去。

所以 `.github/workflows/deploy.yml` 里有这一段：

```yaml
on:
  push:
    branches: [main]
    paths-ignore:
      - 'data/**'      # ← 这一条是必须的，不是优化
```

**改动部署流程时不要删掉它。**

## 三、部署（已配置好，这里是备查）

仓库里已经带了 `.github/workflows/deploy.yml`。第一次部署需要手动开一次 Pages：

1. 打开 https://github.com/chenllAI/GoodLife/settings/pages
2. **Source** 选 **GitHub Actions**（**不要**选 "Deploy from a branch" ——
   那个模式不支持 `paths-ignore`，会被数据提交刷爆构建额度）
3. 保存后，去 **Actions** 标签页看部署进度
4. 部署完成后，链接是 **https://chenllai.github.io/GoodLife/**

之后每次往 `main` 推代码都会自动构建部署。

### 部署到别的仓库

复制 `.env.example` 为 `.env.local`，改成你自己的仓库地址，然后重新构建。
**这里只放仓库地址 —— Token 绝不能写进任何构建变量**，它会被打包进公开的网页。

## 五、几个设计上的决定

### 记录会快照家务的名称和分值

每条积分记录都存下了记录那一刻的家务名、图标、分类、分值和难度，而不是只存一个
家务 id。这样做换来两件事：

- **改家务分值不会改写历史榜单。** 把"拖地"从 5 分调到 7 分，昨天已经记下的那些
  仍然是 5 分。否则昨天的榜单显示"小影 120"，今天打开变成"小影 165" —— 这会被
  理所当然地当成 bug。
- **删掉家务不会让历史记录变成孤儿。** 整理家务列表时删掉某几项，所有历史记录
  仍然完整显示，分类统计也不会凭空少一块。

### 删除记录写的是"墓碑"

删除记录时不是把它从文件里抹掉，而是打一个 `deleted: true` 的标记。
因为在两台设备之间同步时，直接抹掉会被另一台设备的旧副本"复活" ——
你明明删了，刷新一下它又冒出来了。墓碑能在合并时明确表达"这条被删过"。

### 令牌不进构建产物

网页是公开的，Token 一旦写进代码，任何人查看源码就能拿到它，而且会永久留在
git 历史里。所以：

- 构建产物里**只有仓库地址**（公开信息）
- Token 存在各设备的浏览器本地存储里，跟着设备走
- `npm run verify` 会扫描 `dist/`，发现疑似 Token 直接失败
- 邀请链接用 URL fragment 传递令牌，避免它进入服务器日志

### 预置家务会自动升级

预置目录是首次配置时写进数据的。之后如果改了目录（删掉几项、加上"喂鱼"），
应用启动时会比对版本号并自动合并，**不需要清空数据**。

三条保护：你改过名或改过分值的预置项不会被覆盖；你删过的不会复活；
历史积分完全不受影响（有专门的测试覆盖这条）。

### 图标是自动匹配的，不是随便给的

输入家务名后，会按一张关键词规则表打分匹配：`得分 = 关键词长度 × 10 − 出现位置`。
**长度主导**这一点很关键，它让"具体"成为结构性保证而不是靠人肉维护规则顺序：

- 「洗车」命中 `洗车`（20 分），胜过任何更短的词 → 🚗
- 「洗衣服」命中 `洗衣服`（30 分），胜过 `衣服`（20 分）→ 👕
- 「倒厨余垃圾」命中 `倒厨余垃圾`（50 分），胜过 `垃圾`（20 分）→ 🥬

所以这几个都含"洗"或"垃圾"的家务各自归位，不会挤到同一个图标上。

### 配色不是拍脑袋定的

两位成员的配色（小良蓝 `#2a78d6` / 小影橙 `#eb6834`）跑过色盲可辨性校验：
在暖色底 `#FFF7ED` 上，色盲模式下两个颜色的差异是 ΔE 24.7、正常视觉 33.6，
都远超阈值。

另外一条：**颜色跟着"人"走，不跟着"名次"走。** 小影反超的时候，她的条形仍然是
橙色，变的只是头上的皇冠图标。

## 六、已知限制

- **成员固定两个。** 界面按两人对决设计，加第三个人需要改布局。
- **离线时可以记，联网后自动补传。** 记录会排队，顶部会显示待同步条数。
- **时钟不准会导致记到错误的日子。** 应用会从 GitHub 响应头采样时间偏移做校正，
  也可以手动"补录"到过去某一天。
- **预置家务不能删除**，只能隐藏。防止误删后找不回来。自定义的可以删。
- **没有"清空数据"功能。** 真要重置得去 GitHub 仓库手动删 `data/` 下的文件。
- **真实 GitHub API 的几个边界行为尚未在实机验证过**（空仓库首次写入、
  `422` 与 `409` 的确切分界）。代码里对两种状态码都按冲突处理并重试，
  所以不会因此出错。
